# Threat Model: Secure Agent Code Execution Sandbox

**Date:** 2026-10-24  
**Status:** Initial version  
**Scope:** gVisor-based sandbox for AI agent code execution

## System Description

An isolation layer that allows AI agents to execute Python and Bash code without compromising the host system. The sandbox uses gVisor as the runtime to provide an additional security boundary beyond standard container isolation.

## Trust Boundaries

1. **Untrusted**: Code generated by AI agents or provided by users
2. **Sandbox Runtime**: gVisor container runtime
3. **Host System**: The machine running the sandbox
4. **Demo Dashboard**: Static site showing attack test results

## Assets

1. **Host system integrity** - Critical
2. **Host filesystem** - Critical
3. **Network resources** - High (prevent abuse)
4. **CPU/Memory resources** - Medium (prevent DoS)
5. **Execution logs** - Low (may contain sensitive data)

## Threat Categories

### 1. Container Escape

**Threat**: Malicious code breaks out of the sandbox and gains access to the host system.

**Attack Vectors**:
- Kernel exploits through syscall interface
- gVisor vulnerabilities
- Docker daemon exploits
- Privilege escalation within container
- Mount namespace escape
- Device access exploitation

**Mitigations**:
- Use gVisor runtime (not runc) - adds syscall filtering layer
- Run containers as non-root user
- Drop all Linux capabilities
- Read-only filesystem except /tmp
- No privileged containers
- Seccomp profile blocking dangerous syscalls
- AppArmor/SELinux profiles
- No host path mounts
- Separate network namespace

**Residual Risk**: Medium - gVisor provides additional layer but not perfect

### 2. Resource Exhaustion

**Threat**: Code consumes excessive CPU, memory, disk, or execution time, causing denial of service.

**Attack Vectors**:
- Infinite loops
- Fork bombs
- Memory allocation attacks
- Disk fill attacks (/tmp)
- Long-running processes

**Mitigations**:
- CPU limit: 0.5 cores max
- Memory limit: 256MB max
- Execution timeout: 30 seconds
- Max processes (pids limit): 50
- Tmpfs size limit: 100MB
- No swap allowed
- Disk I/O limits

**Residual Risk**: Low - Multiple layers of resource limits

### 3. Network Exfiltration

**Threat**: Code attempts to exfiltrate data or communicate with external systems.

**Attack Vectors**:
- HTTP/HTTPS requests to external sites
- DNS tunneling
- ICMP tunneling
- Connection to C2 servers
- Port scanning
- DDoS participation

**Mitigations**:
- **Default-deny network**: No external network access
- Network mode: none (no network namespace connectivity)
- No DNS resolution
- Firewall rules blocking all egress
- Monitor for network syscalls in logs

**Residual Risk**: Very Low - Network completely disabled

### 4. Persistence

**Threat**: Code attempts to persist across executions or modify the sandbox environment.

**Attack Vectors**:
- Writing to shared volumes
- Modifying container image
- Installing packages that persist
- Cron jobs or systemd services
- ~/.bashrc or similar startup scripts

**Mitigations**:
- Fresh container per execution
- No volumes mounted
- Read-only root filesystem
- Ephemeral /tmp cleared after execution
- No package manager access
- Container destroyed after each run

**Residual Risk**: Very Low - No persistence possible

### 5. Information Disclosure

**Threat**: Code reads sensitive information from the environment or logs.

**Attack Vectors**:
- Environment variable inspection
- Reading /proc filesystem
- Accessing Docker socket
- Reading execution logs
- Timing attacks

**Mitigations**:
- No sensitive data in environment variables
- Minimal /proc exposure (gVisor virtualizes most of it)
- No Docker socket mounted
- Logs sanitized before storage
- No secrets in container
- Synthetic/fake data only for demos

**Residual Risk**: Low - Limited information available

### 6. Abuse as Free Compute

**Threat**: Public demo used as free computation resource (cryptomining, distributed computing, etc.).

**Attack Vectors**:
- Long-running CPU-intensive tasks
- Repeated executions
- Distributed coordination

**Mitigations**:
- **No public execution endpoint** (demo is static dashboard only)
- Rate limiting if ever made interactive
- Execution time limits
- CPU limits
- Per-IP quotas
- Proof-of-work or CAPTCHA

**Residual Risk**: Very Low - No public endpoint planned

### 7. Prompt Injection

**Threat**: User manipulates AI agent through prompt injection to generate malicious code.

**Attack Vectors**:
- Social engineering the AI
- Indirect prompt injection through documents
- Goal hijacking
- Jailbreaking attempts

**Mitigations**:
- **Out of scope**: Application layer responsibility
- Sandbox treats all code as untrusted regardless of source
- Defense in depth - sandbox catches malicious code even if prompt injection succeeds
- Demo uses pre-recorded attack examples, no live AI

**Residual Risk**: Medium - Not addressed by sandbox layer

## Limitations (What gVisor Does NOT Protect Against)

1. **Host kernel vulnerabilities**: If the host kernel has an exploitable bug, gVisor may not prevent exploitation
2. **Hardware side-channel attacks**: Spectre, Meltdown, etc.
3. **Physical access attacks**: Console access, cold boot, etc.
4. **Supply chain attacks**: Compromised base images, gVisor binary, or dependencies
5. **Application logic flaws**: Prompt injection, business logic bypasses
6. **Denial of service at infrastructure level**: Overwhelming the host with containers
7. **Social engineering**: Tricking operators into disabling security features

## Monitoring & Detection

- Syscall audit logs (gVisor provides detailed syscall tracing)
- Resource usage metrics (CPU, memory, disk, execution time)
- Failed escape attempts logged
- Network syscall attempts logged (should be zero)
- Container exit codes
- Anomaly detection: unusual syscall patterns

## Incident Response

1. **Detection**: Monitor logs for anomalous behavior
2. **Containment**: Container auto-destroyed after execution (already contained)
3. **Investigation**: Review syscall audit logs
4. **Recovery**: No recovery needed (fresh container next run)
5. **Lessons Learned**: Update attack catalog and test suite

## Security Assumptions

1. Host OS is kept up to date with security patches
2. Docker and gVisor are from trusted sources
3. Container base image is minimal and verified
4. Operator does not disable security features
5. Demo dashboard does not expose execution API

## Conclusion

This threat model identifies 7 major threat categories and 23 specific attack scenarios. The gVisor-based sandbox provides defense-in-depth against container escape and resource abuse. The primary residual risks are:

1. Host kernel vulnerabilities (mitigated by gVisor layer)
2. Prompt injection (out of scope - application layer)
3. Infrastructure-level DoS (mitigated by not exposing public endpoint)

The attack test suite will validate that all 23 attack scenarios are successfully blocked by the sandbox.
